# FitTracker Pro 프로젝트 정리와 첫 블로그 글

작성일: 2026-10-28. 저장소의 현재 작업 파일, 커밋, 기획·출시 기록과 인접 Admin 저장소의 관련 코드를 읽어 작성했습니다. 외부 게시·배포와 운영 서버 조회는 하지 않았습니다. 코드에 기능이 존재하는 것, 과거 배포 기록이 있는 것, 현재 운영에서 정상 동작하는 것은 구분합니다. 작업 트리에 수정·미추적 파일이 있으므로 현재 코드를 모두 마지막 커밋의 구현으로 설명하지 않습니다.

## 1. 서비스 소개와 개발 계기

FitTracker Pro는 날짜별 운동 종목, 세트, 중량, 반복 횟수와 완료 여부를 기록하고 휴식 시간과 운동량 변화를 확인하는 운동 기록 서비스입니다. 브라우저와 모바일 WebView 앱에서 같은 웹 화면을 사용하며, 카카오 계정을 기준으로 기기간 기록을 동기화합니다. 운동 도감·추천 루틴·운동 코드 가져오기·AI 분석과 오운완 커뮤니티도 연결되어 있습니다.

기능에서 읽을 수 있는 대상 사용자는 운동 중 세트별 기록을 남기고, 다음 운동에서 이전 기록을 참고하며, 다른 기기에서도 기록을 이어 보고 싶은 사람입니다. 이는 구현에서 해석한 사용 대상이며, 인터뷰로 검증한 고객 정의는 아닙니다. 운동 구성을 매번 다시 입력하는 불편은 루틴과 운동 코드로, 완료한 운동을 선택해 공유하는 요구는 오운완으로 다룹니다.

**최초 개발 계기: 확인 필요.** 확인한 문서와 커밋에는 개발자의 개인적인 운동 경험, 기존 서비스에 대한 불만, 최초 제작을 결심한 사건을 입증하는 기록이 없습니다. “제가 운동하다 불편해서 만들었습니다” 같은 서술은 넣지 않습니다.

다만 커뮤니티의 제품 방향은 명시되어 있습니다. `AGENT.md`는 기존 최근 30일 운동 공개 방식 대신, 오늘 운동 전체 완료 후 수동 공유하거나 사용자가 명시적으로 선택한 자동 공유를 적용하도록 정합니다. 이는 확인된 기능 설계 배경이지 서비스 전체의 창업·개발 동기는 아닙니다.

### 기술 선택 이유: 사실과 해석

- **확인된 운영 방침:** 원격 WebView를 사용하므로 일반 웹 변경은 웹 배포로 앱에 반영합니다. 네이티브 브리지·권한 변경은 앱 빌드가 따로 필요합니다. 근거: `AGENTS.md`.
- **확인된 설계 이유:** 오래된 기기 기록이 서버의 최신 기록을 덮지 않도록 조회 → 병합 → 업로드 순서를 유지합니다. 근거: `AGENTS.md`, `firebase-sync.js`.
- **확인된 보안 목적:** 공개 파일만 복사해 기획·설정·네이티브 소스가 정적 자산에 섞이지 않도록 합니다. 근거: `AGENTS.md`, `scripts/build-web.mjs`.
- **해석:** 일반 JavaScript와 정적 자산 구성은 별도 프론트엔드 프레임워크 빌드 없이 화면을 배포하는 구조입니다. 이것이 최초 기술 선택의 이유였는지는 확인되지 않았습니다.
- **확인 필요:** Cloudflare·Next.js·Prisma·Firebase·Gemini를 처음 선택한 개인적 이유, 대안 비교, 비용 판단은 확인한 기록에 없습니다.

## 3. 이야기로 풀어낼 개발 사례

### 사례 A. 오래된 기기 기록이 최신 기록을 덮지 않도록 동기화 순서 정리

**문제 →** 로그인 직후 로컬 기록부터 올리면 다른 기기에서 갱신한 서버 기록이 덮일 수 있습니다. 반대로 서버 기록을 무조건 적용하면 아직 업로드하지 않은 로컬 수정이 사라질 수 있습니다.

**변경 내용 →** 첫 업로드 전에 서버 기록을 조회하고, 날짜별 미업로드 변경을 보호하며 병합합니다. 요청 도중 계정이 바뀌면 이전 계정의 응답을 적용하지 않습니다. 온라인 복귀·화면 재활성화에도 서버 기록을 조회합니다.

**결과 →** 현재 코드와 테스트에서 서버 조회 이후 업로드, 미업로드 변경 보호, 계정 전환 후 응답 무시를 확인할 수 있습니다. 실제 데이터 손실률이나 장애 감소 수치는 없습니다.

근거: `firebase-sync.js`의 `flushGymSync`, `mergeAdminWorkoutsIntoLocalState`, `pullWorkoutsFromAdminServer`; `tests/gym-sync-order.test.cjs`. 관련 과거 커밋: `1db8bb5`, `0afc5d8`. 최신 보호 로직 전체가 이 두 커밋에 포함되었다는 뜻은 아닙니다.

### 사례 B. 지운 운동이 다시 나타나는 문제

**문제 →** 과거 저장 키를 넓게 훑어 합치는 방식은 삭제한 운동을 오래된 데이터에서 다시 가져올 수 있었습니다.

**변경 내용 →** 현재 상태를 우선하고, 이전 저장 형식은 제한적으로 마이그레이션하도록 변경했습니다. 현재 코드에는 삭제 날짜를 동기화에 전달하고 병합에서 제외하는 처리도 있습니다.

**결과 →** 커밋 diff에서 광범위한 저장소 검색을 제거한 변경을 확인했습니다. 모든 저장 경로에서 재발하지 않는다고 보장하는 운영 검증은 이번 작업에서 수행하지 않았습니다. 특히 Firestore 경로는 별도로 존재합니다.

근거: 커밋 `0ece115`의 `app.js`, `firebase-sync.js`; 현재 `searchAndCollectAllLocalWorkouts`, `deletedDates` 처리.

### 사례 C. 공유 여부를 사용자가 선택하는 오운완

**문제 →** 커뮤니티에 들어가는 것과 개인 운동 기록을 공개하는 것이 묶여 있던 기존 기획을 바꿀 필요가 있었습니다.

**변경 내용 →** 닉네임 설정으로 입장하고, 오늘 모든 세트를 완료한 뒤 공유를 선택하게 했습니다. 자동 공유는 명시적으로 켜야 하며, 게시물은 개인 기록 전체가 아닌 공개용 스냅샷으로 구성합니다. 계정·날짜 유일 제약으로 하루 게시물 중복을 제한합니다.

**결과 →** 입장과 공유를 분리한 코드가 있고 2026-09-13 출시 기록이 남아 있습니다. 가입률·공유율 증가를 입증하는 자료는 없습니다.

근거: `AGENT.md`, `ouwan.js`, `ouwan-core.js`, `community-auth.js`, `tests/ouwan-core.test.cjs`; Admin `src/lib/ouwan.ts`, `prisma/schema.prisma`; `planning/releases/2026-09-13-ouwan.md`. 현재 일부 파일은 미추적 상태이므로 대응 커밋은 특정하지 않았습니다.

### 사례 D. 운동 구성을 복사하되 완료 결과는 복사하지 않기

**문제 →** 다른 사람의 운동을 가져올 때 완료 표시까지 유지하면 내 운동을 이미 수행한 것처럼 보일 수 있습니다. 기존 기록을 덮어쓰거나 휴식 시간이 사라지는 것도 피해야 합니다.

**변경 내용 →** 운동 코드 생성 로직을 공통화하고 공유용 완료 상태를 초기화합니다. 가져올 날짜·종목을 선택하고, 같은 이름의 운동은 건너뛰며 휴식 시간을 유지합니다.

**결과 →** 코드와 테스트에 완료 초기화·휴식 유지·기존 기록 보존 조건이 있습니다. “가져오기”와 “운동 완료 인증”이 별개 동작으로 구현되어 있습니다.

근거: `routine-code.js`, `community-import.js`, `tests/community-import.test.cjs`, `tests/ouwan-core.test.cjs`.

### 사례 E. 차트에서 볼 정보를 줄이기

**문제 →** 성장 차트에는 여러 지표와 비교 UI가 누적되어 있었습니다. 사용자 조사로 복잡성을 측정한 기록은 없습니다.

**변경 내용 →** 커밋에서 성장 차트를 총 운동량 중심으로 단순화하고 터치한 날짜의 상세 카드를 연결했습니다.

**결과 →** 지표 구성과 상호작용이 바뀐 사실을 diff로 확인했습니다. 렌더링 속도나 사용성 개선율을 측정한 결과는 아닙니다.

근거: 커밋 `ac61b94`, 관련 파일 `app.js`, `index.html`, `style.css`. 다중 지표 도입 기록은 `f54faa5`.

### 사례 F. 배포할 파일을 명시적으로 제한하기

**문제 →** 저장소에는 웹 파일 외에도 네이티브 소스·운영 문서·설정이 있습니다. 루트 전체를 공개하면 불필요한 파일도 배포될 수 있습니다. 실제 유출 사고가 있었다는 기록은 확인하지 않았습니다.

**변경 내용 →** 빌드 스크립트의 공개 파일 목록만 `dist/`에 복사하고, Worker의 자산 경로도 `dist/`로 제한합니다.

**결과 →** 현재 설정에서 기획 문서와 네이티브 소스를 배포 대상에서 분리합니다. 출시 기록에는 공개 빌드 제외 확인과 변경 자산 해시 대조가 기재되어 있습니다. 이 문서도 `planning/`에 두어 현재 공개 목록에 포함되지 않습니다.

근거: `scripts/build-web.mjs`, `wrangler.jsonc`, `AGENTS.md`, 두 출시 기록.

## 4. AI와 개발한 과정과 프롬프트

### 실제 기록의 범위

확인한 저장소에는 기능 요구·구현·검증·출시를 정리한 문서가 있지만, 개발자가 AI에게 보낸 개발 요청 원문과 AI 응답을 연속해서 확인할 수 있는 대화 로그는 찾지 못했습니다. 커밋만으로 특정 AI 도구·모델이 코드를 작성했다고 단정할 수 없습니다. AI 기여 비율, 절약 시간, 최초 사용 모델도 확인 필요입니다.

FitTracker Pro는 날짜별 운동을 기록하고, 이전 기록을 참고하면서 다음 운동을 이어 갈 수 있도록 만든 서비스입니다. 최초에 어떤 개인적인 경험으로 개발을 시작했는지는 현재 남아 있는 문서만으로 확인하기 어렵습니다. 개발 계기는 별도 확인이 필요하므로, 이번 글에서는 코드와 변경 기록에서 확인할 수 있는 기능과 해결 과정을 중심으로 소개하겠습니다.

운동 기록에는 종목 이름만 필요한 것이 아닙니다. 같은 종목이라도 세트마다 중량과 반복 횟수가 다르고, 어떤 세트를 마쳤는지도 구분해야 합니다. FitTracker Pro에서는 날짜별로 운동을 추가하고 세트의 중량, 횟수와 완료 여부를 기록합니다. 휴식 타이머를 함께 사용하고, 쌓인 기록은 운동량 차트에서 확인할 수 있습니다. 운동 중 입력하고 나중에 돌아보는 흐름을 한 화면의 기능들로 연결한 구성입니다.

운동 구성을 반복해서 입력하는 일을 줄이는 기능도 있습니다. 추천 루틴을 가져오거나 운동 코드를 복사해 사용할 수 있습니다. 커뮤니티에서 다른 사람의 운동을 가져올 때는 중량과 횟수, 휴식 시간 같은 구성을 유지하되 완료 상태는 초기화합니다. 누군가가 수행한 결과를 참고하는 것과 내가 그 운동을 끝낸 것은 다르기 때문입니다. 같은 이름의 운동이 이미 있는 경우에는 건너뛰어 기존 기록을 보존합니다.

웹 화면은 HTML, CSS와 JavaScript로 구성되어 있고, 차트에는 Chart.js를 사용합니다. 기록을 브라우저에 저장하는 경로가 있으며, 카카오 계정을 기준으로 다른 기기와 기록을 맞추는 서버 API도 연결되어 있습니다. 별도 서버는 Next.js와 TypeScript로 작성되어 있고 Prisma를 통해 PostgreSQL의 운동·커뮤니티 데이터를 다룹니다. Firebase 인증과 Firestore 코드도 남아 있지만, 기기간 동기화의 기준은 별도 서버입니다.

이 구조에서 중요했던 문제 중 하나는 동기화 순서였습니다. 휴대폰에서 운동을 기록한 뒤 오래 사용하지 않은 PC로 로그인하는 상황을 생각해 볼 수 있습니다. 이때 PC에 남아 있는 기록을 먼저 올리면 서버의 최신 기록을 덮을 수 있습니다. 현재 구현은 첫 업로드 전에 서버 기록을 불러오고 로컬 기록과 병합하도록 되어 있습니다. 온라인으로 돌아오거나 화면이 다시 활성화될 때도 서버 기록을 확인합니다.

그렇다고 서버 기록으로 모든 로컬 데이터를 바꾸는 것도 충분하지 않습니다. 기기에서 막 수정했지만 아직 업로드하지 않은 내용이 있을 수 있기 때문입니다. 그래서 변경된 날짜를 구분해 보호하고, 요청 중 계정이 바뀌면 이전 계정의 늦은 응답을 적용하지 않도록 했습니다. 관련 테스트에는 조회가 업로드보다 먼저 실행되는지, 로컬 수정이 남는지, 다른 계정의 응답을 무시하는지 확인하는 조건이 있습니다. 이는 코드와 테스트에서 확인한 내용이며, 실제 장애가 얼마나 줄었는지를 측정한 결과는 아닙니다.

삭제한 기록이 다시 나타나는 문제도 변경 기록에 남아 있습니다. 과거에는 여러 저장 키에 흩어진 운동을 폭넓게 수집했지만, 이 방식은 이미 지운 데이터를 다시 가져올 가능성이 있었습니다. 이후 현재 상태를 우선하고 이전 저장 형식은 제한적으로 옮기도록 정리했습니다. 데이터를 많이 찾아 합치는 것만으로 동기화가 완성되지는 않습니다. 사용자가 지웠다는 의도도 저장과 병합 과정에 반영해야 한다는 점을 보여 주는 사례입니다.

커뮤니티인 오운완은 운동을 완료한 날을 공유하고 서로 응원하는 공간입니다. 최신 기획에서 분명하게 바뀐 부분은 입장과 공개를 분리한 것입니다. 닉네임을 설정해 커뮤니티에 들어가는 것만으로 과거 운동이 공개되지는 않습니다. 오늘 등록한 모든 세트를 완료한 뒤 공유를 선택하며, 자동 공유도 사용자가 명시적으로 켜야 합니다. 개인 기록과 공개 게시물은 별도로 다루고, 같은 계정이 같은 날짜에 게시물을 중복 생성하지 않도록 제한합니다.

공유 화면을 만드는 일은 버튼을 추가하는 것으로 끝나지 않습니다. 공유 창을 연 뒤 완료를 해제하거나, 다른 기기에서 기록을 수정하거나, 통신이 끊길 수도 있습니다. 오운완의 기획과 구현에는 이런 상황에서 완료 상태와 계정을 다시 확인하는 처리가 담겨 있습니다. 다른 사람에게 보여 줄 데이터는 개인 기록을 그대로 노출하기보다, 공개하기로 한 항목을 기준으로 구성합니다. 공유 실패가 개인 운동 저장을 방해하지 않도록 흐름을 나누는 것도 중요한 조건입니다.

운영에서는 웹과 네이티브 앱의 역할을 구분합니다. Android와 iOS 앱은 원격 웹 화면을 표시하므로 일반적인 화면 변경은 웹 배포로 반영할 수 있습니다. 반면 로그인 연결이나 사진 공유처럼 네이티브 브리지에 손대는 변경은 앱 빌드가 필요합니다. 웹 배포 자체도 저장소 전체를 올리는 방식이 아니라, 공개할 파일을 명시한 목록으로 구성합니다. 기획 문서와 개발 설정이 사용자에게 전달되는 정적 파일에 섞이지 않도록 하기 위해서입니다.

이 프로젝트의 변경 기록에서 읽을 수 있는 교훈은 기능이 생겼다는 사실만큼 데이터가 이동하는 조건이 중요하다는 점입니다. 기록을 먼저 읽을지 쓸지, 삭제를 어떻게 기억할지, 다른 사람의 운동에서 무엇을 가져올지, 언제 공개에 동의한 것으로 볼지가 실제 동작을 결정합니다. 앞으로의 개발기를 정리할 때도 기능 목록보다 이런 판단을 중심으로 설명하려고 합니다. 성능이나 사용성의 개선 폭은 측정한 자료가 생겼을 때 별도로 다루겠습니다.

## 확인이 필요한 사항

- 최초 개발 동기, 처음 해결하고 싶었던 개인적 불편, 실제 목표 사용자와 사용자 피드백.
- AI와 개발할 때 사용한 도구·모델, 실제 요청 원문, 사람이 검토·수정한 범위. 대화 내보내기가 있다면 개인정보·비밀값을 제거한 뒤 추가 검토 가능.
- 기술별 최초 선택 이유와 비교했던 대안. 코드 구조만으로 비용·성능·생산성 동기를 단정할 수 없음.
- 미커밋 파일 각각의 완료·검증·배포 상태와 현재 운영본과의 차이. 과거 출시 문서만으로 현재 운영 상태를 보증하지 않음.
- iOS 스토어 출시 상태, Android 업데이트의 사용자별 노출 상태, AI 기능의 현재 가용성과 실제 선택 모델.
- Firestore 경로와 Admin 동기화 경로가 함께 동작할 때의 삭제·복원 정책, 기존 계정 호환 인증의 보장 범위. 이번 문서는 보안 감사가 아님.
- 실제 이용자 수, 기록 유지율, 공유율, 장애 감소율, 응답 시간과 비용. 측정 자료가 없으므로 성과 수치를 쓰지 않음.

이 파일은 문서 초안으로만 작성했으며 외부 게시·배포하지 않았습니다. 비밀키·토큰·개인정보·내부 접속 정보는 수록하지 않았습니다.
